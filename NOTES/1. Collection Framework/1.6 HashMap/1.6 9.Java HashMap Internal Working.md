# Java HashMap – How HashMap Works Internally

## 1. Introduction

A Java `HashMap` stores data in the form of:

```text
Key -> Value
```

For example:

```java
map.put("name", "Ramesh");
```

Here:

```text
Key   = "name"
Value = "Ramesh"
```

The important questions are:

1. How does `HashMap` decide where to store this entry?
2. How does `HashMap` quickly find `"Ramesh"` when we call `get("name")`?
3. What happens when multiple keys are mapped to the same bucket?
4. When and why does a `HashMap` resize?

---

# 2. High-Level Internal Structure

Internally, a `HashMap` uses an array of buckets.

Conceptually:

```text
HashMap
   |
   v
Bucket Array
   |
   +---- [0]
   +---- [1]
   +---- [2]
   +---- [3] ---> Entry
   +---- [4]
   +---- [5]
   ...
```

Each stored entry contains information such as:

```text
Entry
 |
 +-- hash
 +-- key
 +-- value
 +-- next
```

The `next` reference is useful when multiple entries occupy the same bucket.

---

# 3. Complete HashMap Flow

The overall process can be summarized as:

```text
Key + Value
    |
    v
hashCode()
    |
    v
Hash Bit Spreading
    |
    v
Calculate Bucket Index
    |
    v
Bucket
    |
    +---- Empty?
    |       |
    |       +---- Yes -> Store Entry
    |
    +---- Collision?
            |
            +---- List / Tree
```

For retrieval:

```text
Key
 |
 v
hashCode()
 |
 v
Spread Hash
 |
 v
Calculate Bucket
 |
 v
Compare Hash
 |
 v
Compare Key using == / equals()
 |
 v
Return Value
```

---

# 4. Step 1 – Create a Key-Value Pair

Consider:

```java
map.put("name", "Ramesh");
```

Here:

```text
Key   = name
Value = Ramesh
```

Internally, `HashMap` needs to determine which bucket should contain this entry.

The entry conceptually contains:

```text
Entry
 |
 +-- key   = name
 +-- value = Ramesh
 +-- hash  = calculated hash
 +-- next  = reference to another entry if required
```

---

# 5. Keys Must Be Unique

A `HashMap` does not allow duplicate keys.

For example:

```java
map.put("name", "Ramesh");
map.put("name", "Sanjay");
```

The second call does not create another `"name"` key.

Instead, the existing value is updated.

Conceptually:

```text
Before:

name -> Ramesh


After:

name -> Sanjay
```

Therefore:

> **Keys are unique, but values can be duplicated.**

---

# 6. Step 2 – Calculate the Hash

When we insert a key, `HashMap` first obtains its hash code.

Conceptually:

```java
key.hashCode();
```

Suppose:

```text
key = "name"

hashCode = 35
```

However, `HashMap` does not simply use the raw `hashCode()` result directly for bucket selection.

It performs an internal hash-spreading operation.

---

# 7. Hash Bit Spreading

The purpose of hash spreading is to mix some higher bits of the hash code into the lower bits.

Conceptually:

```text
Original hashCode
       |
       v
Bit mixing / spreading
       |
       v
Internal HashMap hash
```

Why is this useful?

Because the lower bits play an important role when calculating the bucket index.

Better distribution means:

```text
Better Hash Distribution
        |
        v
Fewer Collisions
        |
        v
Better Performance
```

For our beginner-friendly example, assume:

```text
Original hashCode = 35
Mixed hash        = 35
```

---

# 8. Step 3 – Calculate the Bucket Index

`HashMap` internally maintains an array of buckets.

Suppose the current capacity is:

```text
16
```

Then the bucket indexes are:

```text
0 to 15
```

Conceptually:

```text
Bucket Array

[0]
[1]
[2]
[3]
[4]
...
[15]
```

---

# 9. Bucket Index Formula

The bucket index is calculated using:

```text
index = (n - 1) & hash
```

where:

```text
n    = current table capacity
hash = processed/spread hash
&    = bitwise AND
```

Suppose:

```text
n    = 16
hash = 35
```

Then:

```text
index = (16 - 1) & 35

index = 15 & 35

index = 3
```

Therefore:

```text
"name" -> "Ramesh"
```

will be placed in:

```text
Bucket 3
```

---

# 10. Why Does This Formula Work?

`HashMap` uses capacities that allow this bitwise operation to efficiently map a hash to a valid bucket index.

For:

```text
capacity = 16
```

the possible indexes are:

```text
0 - 15
```

Therefore:

```text
(n - 1) & hash
```

produces an index within the bucket array.

---

# 11. Step 4 – Store the Entry

After calculating:

```text
index = 3
```

`HashMap` goes to:

```text
Bucket 3
```

If bucket 3 is empty:

```text
Bucket 3
   |
   v
EMPTY
```

the new entry is stored there:

```text
Bucket 3
   |
   v
[name, Ramesh]
```

---

# 12. Internal Picture

Conceptually:

```text
HashMap Bucket Array

Index
  |
  v

[0] -> null

[1] -> null

[2] -> null

[3] -> [name = Ramesh]

[4] -> null

[5] -> null

...

[15] -> null
```

This is the simple case where no collision occurs.

---

# 13. What Is a Hash Collision?

Different keys can sometimes calculate to the same bucket index.

This situation is called:

> **Hash Collision**

For example:

```text
name     -> Ramesh
nickname -> Ram
```

Suppose both entries calculate:

```text
Bucket Index = 3
```

Now both entries need to exist inside bucket 3.

---

# 14. Collision Does NOT Mean Duplicate Key

This distinction is very important.

Suppose:

```text
Key 1 = name
Key 2 = nickname
```

Both may calculate the same bucket:

```text
Bucket 3
```

But:

```text
"name" != "nickname"
```

Therefore, both entries can exist.

Conceptually:

```text
Bucket 3
   |
   v
[name = Ramesh]
   |
   v
[nickname = Ram]
```

One does not automatically replace the other because the keys are different.

---

# 15. Collision vs Duplicate Key

These are different concepts.

### Collision

```text
Different Keys
     +
Same Bucket
```

Example:

```text
name     -> Ramesh
nickname -> Ram
```

Both remain in the map.

### Duplicate Key

```text
Same Key
```

Example:

```java
map.put("name", "Ramesh");
map.put("name", "Sanjay");
```

The value is updated:

```text
name -> Sanjay
```

---

# 16. Step 5 – Collision Handling

When multiple entries belong to the same bucket, `HashMap` can organize them using:

```text
Linked Structure
```

or, when certain conditions are met:

```text
Red-Black Tree
```

For a small number of entries, conceptually:

```text
Bucket 3
   |
   v
Entry 1
name -> Ramesh
   |
   v
Entry 2
nickname -> Ram
```

---

# 17. Why Convert a Bucket to a Tree?

Suppose many keys collide into the same bucket.

A long list can make lookup slower.

Conceptually:

```text
Bucket
 |
 v
Entry
 |
 v
Entry
 |
 v
Entry
 |
 v
Entry
 |
 v
Entry
 ...
```

Searching through many entries can become expensive.

Therefore, modern Java `HashMap` implementations can convert a heavily populated bucket into a:

> **Red-Black Tree**

---

# 18. Treeification

In the OpenJDK implementation discussed in the lecture, treeification becomes possible when the bucket reaches approximately:

```text
8 entries
```

This is commonly associated with:

```text
TREEIFY_THRESHOLD = 8
```

However, the complete table must also have sufficient capacity.

The lecture uses:

```text
Minimum table capacity = 64
```

If the table capacity is below this level, `HashMap` normally prefers resizing rather than immediately converting the bucket into a tree.

---

# 19. Treeification Diagram

Before treeification:

```text
Bucket
 |
 v
Node
 |
 v
Node
 |
 v
Node
 |
 v
Node
 |
 v
...
```

After treeification:

```text
            Node
           /    \
        Node    Node
       /   \    /  \
    Node  Node Node Node
```

The actual implementation uses a red-black tree.

---

# 20. Untreeification

If a tree-based bucket later becomes sufficiently small, it may be converted back into a list-like structure.

The lecture mentions the untreeification threshold:

```text
6
```

commonly associated with:

```text
UNTREEIFY_THRESHOLD = 6
```

Conceptually:

```text
Many collisions
      |
      v
Linked Structure
      |
      v
Red-Black Tree
      |
entries decrease
      v
Linked Structure
```

---

# 21. Step 6 – Retrieve a Value

Now suppose we call:

```java
map.get("name");
```

`HashMap` needs to locate:

```text
Ramesh
```

It repeats the important hashing steps.

---

# 22. Retrieval Process

Conceptually:

```text
get("name")
     |
     v
"name".hashCode()
     |
     v
Spread Hash Bits
     |
     v
Calculate Bucket Index
     |
     v
Bucket 3
     |
     v
Find Matching Entry
     |
     v
Return "Ramesh"
```

Because the same key is used, the same hashing process leads `HashMap` to the appropriate bucket.

---

# 23. Why HashMap Lookup Is Fast

`HashMap` does not normally need to scan every entry.

Instead:

```text
Key
 |
 v
Hash
 |
 v
Bucket Index
 |
 v
Specific Bucket
```

This allows it to go directly to a likely location.

That is one of the main reasons why `HashMap` provides very fast average lookup performance.

---

# 24. How Does HashMap Find the Correct Entry Inside a Bucket?

Once the correct bucket is located, `HashMap` needs to identify the correct key.

The lecture describes the process as:

1. Compare the stored hash
2. Compare the keys
3. Check whether they are the same object or equal according to `equals()`

Conceptually:

```text
Correct Bucket
      |
      v
Compare Hash
      |
      v
Compare Key
      |
      +---- Same object?
      |
      +---- equals()?
      |
      v
Matching Key
      |
      v
Return Value
```

---

# 25. Importance of hashCode() and equals()

Two methods are extremely important when objects are used as `HashMap` keys:

```java
hashCode()
equals()
```

`hashCode()` helps determine the bucket.

`equals()` helps determine whether the correct key has been found.

A useful mental model is:

```text
hashCode()
    |
    +---- "Where should I look?"


equals()
    |
    +---- "Is this the correct key?"
```

---

# 26. equals() and hashCode() Contract

A critical rule is:

> If two objects are equal according to `equals()`, they must produce the same `hashCode()`.

Conceptually:

```java
a.equals(b) == true
```

must imply:

```java
a.hashCode() == b.hashCode()
```

This rule is extremely important when custom objects are used as keys.

---

# 27. Custom Key Problem

Suppose we create:

```java
class EmployeeKey {
    private int id;
}
```

and use it as:

```java
Map<EmployeeKey, String> map =
        new HashMap<>();
```

If `equals()` and `hashCode()` are implemented inconsistently, `HashMap` may not behave as expected when retrieving entries using logically equivalent key objects.

Therefore:

> **When creating custom HashMap keys, implement `equals()` and `hashCode()` consistently.**

---

# 28. Prefer Immutable Keys

Another important recommendation is:

> **Prefer immutable objects as HashMap keys.**

Suppose a key's hash code depends on:

```text
employeeId
```

You insert the key:

```text
employeeId = 101
        |
        v
Hash
        |
        v
Bucket 3
```

Later, suppose the key object is modified:

```text
employeeId = 999
```

Its hash code may now change.

During retrieval:

```text
employeeId = 999
        |
        v
Different Hash
        |
        v
Different Bucket
```

The entry is still physically stored according to the earlier hash/bucket placement.

This can make the entry difficult or impossible to retrieve using the modified key as expected.

---

# 29. Key Design Rules

When designing objects used as `HashMap` keys:

### Rule 1

Implement:

```java
equals()
hashCode()
```

consistently.

### Rule 2

Prefer immutable keys.

### Rule 3

Do not modify fields used by:

```java
equals()
hashCode()
```

after inserting the key.

### Rule 4

Remember that keys are unique.

---

# 30. Step 7 – HashMap Resizing

As more entries are added, the bucket array can become crowded.

More crowded buckets can increase the probability of collisions.

To maintain efficient performance, `HashMap` can resize its internal table.

---

# 31. Load Factor

`HashMap` uses a:

> **Load Factor**

to help determine when resizing should occur.

The default load factor discussed in the lecture is:

```text
0.75
```

The threshold is conceptually calculated as:

```text
threshold = capacity × load factor
```

---

# 32. Resize Example

Suppose:

```text
Capacity    = 4
Load Factor = 0.75
```

Then:

```text
Threshold
    =
4 × 0.75
    =
3
```

Conceptually:

```text
Capacity = 4

[0]
[1]
[2]
[3]

Threshold = 3
```

As the number of entries grows beyond the threshold, resizing occurs.

---

# 33. Capacity Usually Doubles

During resizing, the internal capacity usually doubles.

For example:

```text
4 -> 8
```

or:

```text
8 -> 16
```

or:

```text
16 -> 32
```

Conceptually:

```text
Before Resize

Capacity = 4

[0]
[1]
[2]
[3]


After Resize

Capacity = 8

[0]
[1]
[2]
[3]
[4]
[5]
[6]
[7]
```

---

# 34. Entries Are Redistributed

When the table grows, existing entries are redistributed according to the new table structure.

Conceptually:

```text
Old Table
Capacity = 4

      |
      | Resize
      v

New Table
Capacity = 8

      |
      v

Entries distributed
across new buckets
```

This helps reduce collisions and maintain efficient operations.

# 35. HashMap Characteristics

Important characteristics of `HashMap` include:

| Characteristic | HashMap |
|---|---|
| Stores key-value pairs | Yes |
| Duplicate keys | No |
| Duplicate values | Yes |
| Null key | One allowed |
| Null values | Multiple allowed |
| Maintains insertion order | No guarantee |
| Thread-safe by default | No |
| Synchronized by default | No |

---

# 36. Null Key

`HashMap` allows one `null` key.

Example:

```java
map.put(null, "Ramesh");
```

If another value is added with the same `null` key:

```java
map.put(null, "Sanjay");
```

the existing value is replaced because there can only be one mapping for a particular key.

---

# 37. Multiple Null Values

Multiple keys can have `null` values.

Example:

```java
map.put("A", null);
map.put("B", null);
map.put("C", null);
```

This is valid.

Conceptually:

```text
A -> null
B -> null
C -> null
```

---

# 38. HashMap Does Not Guarantee Order

A `HashMap` does not guarantee insertion order or any fixed iteration order.

For example:

```java
map.put("Apple", 10);
map.put("Banana", 20);
map.put("Orange", 15);
```

You should not depend on iteration producing:

```text
Apple
Banana
Orange
```

in that exact order.

If insertion order is required, a different map implementation such as `LinkedHashMap` may be appropriate.

---

# 39. HashMap Is Not Thread-Safe by Default

`HashMap` is not synchronized by default.

Therefore, it is not designed to provide thread-safe concurrent modification automatically.

For concurrent scenarios, Java provides alternatives such as:

```java
ConcurrentHashMap
```

depending on the application's requirements.

---

# 40. HashMap Performance

Average-case performance for common operations is expected to be approximately:

| Operation | Average Case |
|---|---:|
| `put()` | O(1) |
| `get()` | O(1) |
| `remove()` | O(1) |
| `containsKey()` | O(1) |

This assumes hashes are distributed reasonably well.

---

# 41. Collision Performance

If many entries occupy the same bucket and are represented using a list-like structure, searching within that bucket can become slower.

Conceptually:

```text
Entry 1
   |
   v
Entry 2
   |
   v
Entry 3
   |
   v
Entry 4
   |
   v
...
```

In a heavily collided list, lookup can approach:

```text
O(n)
```

---

# 42. Tree-Based Bucket Performance

When a heavily populated bucket is converted into a red-black tree, lookup performance can improve toward:

```text
O(log n)
```

Therefore:

```text
Normal well-distributed HashMap
        |
        v
Average O(1)


Heavy collision + linked structure
        |
        v
Can approach O(n)


Treeified bucket
        |
        v
Can improve toward O(log n)
```

# 46. Important Interview Questions

## How does HashMap work internally?

At a high level:

1. Obtain the key's `hashCode()`
2. Spread/mix the hash bits
3. Calculate the bucket index
4. Store the entry in the corresponding bucket
5. Handle collisions when multiple keys share a bucket
6. Use hash and key equality during retrieval
7. Resize when the threshold is exceeded

---

## What is a bucket?

A bucket is a position inside the internal HashMap table where entries are stored.

Conceptually:

```text
Bucket Array

[0]
[1]
[2]
[3] -> Entry
[4]
...
```

---

## What is a hash collision?

A collision occurs when different keys are mapped to the same bucket.

Example:

```text
Key A ----+
          |
          +----> Bucket 3
          |
Key B ----+
```

Both entries can still exist because their keys are different.

---

## How does HashMap handle collisions?

It can maintain multiple entries in the same bucket using a list-like structure.

When a bucket becomes heavily populated and the required conditions are satisfied, it can be converted into a red-black tree.

---

## Why are equals() and hashCode() important?

`hashCode()` helps determine where the key should be searched.

`equals()` helps determine whether the correct key has been found.

Remember:

```text
hashCode() -> WHERE?

equals()   -> WHICH ONE?
```

---

## What is the default load factor?

The lecture identifies the default load factor as:

```text
0.75
```

---

## What is the resize threshold?

Conceptually:

```text
threshold = capacity × load factor
```

Example:

```text
capacity = 4
load factor = 0.75

threshold = 3
```

---

## What happens during resizing?

The internal table becomes larger, usually by doubling its capacity, and entries are redistributed according to the new table structure.

---

## Why should HashMap keys preferably be immutable?

Because modifying fields that affect `equals()` or `hashCode()` after insertion can change how the key hashes.

The entry may then no longer be found as expected.

---

# 50. Final Revision

The complete process can be remembered in seven steps:

### Step 1

Receive:

```text
Key + Value
```

### Step 2

Calculate:

```text
hashCode()
    +
hash spreading
```

### Step 3

Calculate:

```text
Bucket Index
```

using:

```text
(n - 1) & hash
```

### Step 4

Store the entry in the calculated bucket.

### Step 5

Handle collisions using a list-like structure or, under the required conditions, a red-black tree.

### Step 6

During retrieval, use the hash and key comparison/`equals()` to locate the correct entry.

### Step 7

When the map grows beyond its threshold, resize the bucket array and redistribute entries.

# Key Takeaway

The most important idea is:

> **HashMap uses the key's hash to quickly determine where an entry should be stored and searched.**

The simplified internal flow is:

```text
KEY
 |
 v
hashCode()
 |
 v
Hash Spreading
 |
 v
Bucket Index
 |
 v
Bucket
 |
 v
equals()
 |
 v
VALUE
```

Remember:

```text
hashCode() -> Helps find the bucket

equals()   -> Helps identify the correct key
```

And for good custom keys:

```text
1. Implement equals() correctly
2. Implement hashCode() consistently
3. Prefer immutable keys
4. Do not modify hash-related fields after insertion
```

This combination is fundamental to understanding why Java `HashMap` can provide very fast key-based storage and retrieval.
